开跑前发现原 R5 一题需要工具不支持的区间推导操作，零调用即拒绝并保留记录；只替换为直接原文容量求和的 R5B-R01，其他五题保持一致且此前未运行。R5 与 R5b 共用同一额度，没有重新获得预算。

## 可确认的收益与尚未完成的覆盖

- 合格的来源冲突／未知固定稿，候选正常放行，基线误拦；错误的版本、人工复核和导出完成声明，两版都拦截。
- 长文候选自动准备在约 11.5 秒内完成；三组规则、末尾例外和事实所需的 9 段原文均实际进入工作模型输入，生成过真实的 40 页求和回执。两个相同计算请求返回同一回执，第二次校验会重新求值，但模型看不到独立执行事件，于是要求补证并申请未开放的 `run_code`。数值正确仍没有最终稿，不能记为端到端成功。
- 文件场景候选实际读取新增巡检全文 2 次，基线 1 次；材料进入规划模型，但两版工作模型均未在导入后恢复。两版反复调用的 `read_local_result` 只支持本地代码执行结果，不支持 `write_file`；候选没有实际调用新增的 `action_status` 文件观察能力。因此本题未验证到这项修复。该场景占候选 216,506 tokens，约 44.3%，应优先处理重复工具调用和交接阻塞。
- 候选两份修订初稿业务内容合格，并通过事项核验；执行器没有执行委派整体检查，就调用了验收。产品正确抛出 `COMPLETION_REQUIRED`，实际修订阶段均未运行。这是本轮执行器缺陷，不记作模型误拦。
- 候选 25 次输入均记录预算且适配，全部为 level 0；没有覆盖超额压缩恢复。回执别名出现 3 次，精确展开一致，减少 2,371 个序列化字符；这不是实测 token 节省量。

评审另以两份真实快照做零真实调用的离线复现：恢复同等授权后，原事项核验依据保持一致，直接验收均被整体检查门槛拒绝；走生产 `agent.run` 的 `complete` 和整体核验后，均可正常验收。离线模拟结果不补记为真实修订成功。

文件夹具还存在一个尚未触发的冲突：为历史文件回读设置 `useOutputFolder=true`，会要求未来的主报告也写入文件，而题目明确禁止新写入。实际运行尚未到此门槛，不能将它当作已经发生的循环原因；下轮必须修正。先前代码审核和开跑前审核未发现这两个生命周期覆盖缺口，本轮保留原记录，不倒填“审核通过”结论。

基线曾从磁盘读取历史索引，但新观察被暂存为 pending，正文没有交给模型，历史全文比较也未完成；这与“文件完全没有被读取”不同。巡检全文在基线 5 个、候选 4 个规划输入中可见，在补证后的工作输入中均未出现。独立结果审核的 71 项映射与算术检查通过。

## 下一步顺序

先修评测执行器的完整生命周期，用离线真实状态链证明“事项通过 → 委派整体检查 → 验收 → 改要求 → 重开 → 修订 → 再核验”能闭环；不能删除产品的整体检查门槛来让测试通过。

随后处理工作模型与规划模型的工具交接：已知可执行的计算、文件观察和授权读取应有明确路由，失败的工具与参数组合不能无限重复；补到证据后要恢复原事项。计算结果身份与执行事件身份应分开：保留结果复用，同时提供可核对的执行／重新验证记录，不能靠给相同结果换 ID 冒充两次执行。先完成离线回归和独立审核，再制定下一轮全新样本与预算。本轮不追加真实调用，也不以同题调参后的复跑充当独立验收。

待流程可靠后再检验 token 优化。应按成功闭环任务比较成本，并分别记录生成、规划、补证、核验及重复请求；A–D 正式验收通过后再抽取 Windows/macOS 公共模块。本轮测试主机为 Windows，未验证 macOS 打包与原生集成。
