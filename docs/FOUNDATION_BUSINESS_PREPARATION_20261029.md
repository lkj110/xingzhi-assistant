## 独立确认的产品根因

F05 修订初检经历读取耗尽后的有界结论，产品把该检查身份持久记录为 `returned`。该结论要求人工确认表达；随后通过实际 UI 保存的确认记录准确绑定当前报告、证据 basis 和两条片段，稿件、要求、来源和报告未变。

但 `check-finalization.identity` 的身份基于输入、稿件和 `acceptance.basis`，后者不包含这次受信任的人工确认。显式重检仍落入已消费的检查身份，在模型调用前得到“本检查的有界结论已登记或旧记录身份不明；请核对原请求，不能再次调用”。独立只读复算也确认：即使换一个 legacy key，相同 semantic check ID 仍被 `semantic_consumed` 拒绝。这是静态诊断，未为此追加应用或模型运行。

因此问题在“有界结论防重复调用”与“人工确认后必须重新核验”两套协议的衔接。它不是模型幻觉、token 超额、无效确认或格式错误，也不能通过扩大评测额度解决。本轮没有把核验替身全部改成直接通过来避开此分支。

## 下一步仅修一个候选协议边界

建议在后续独立补丁中，为“受信任、与当前报告/稿件/要求/来源完整绑定的人工确认＋显式重检”建立独立、持久化且不可重放的检查授权。保留历史有界结论记录，保留证据绑定和语义标准，保留真人最终验收，不扩大自动重试权限；当前安装基础版继续冻结。

该补丁的结束条件为：

1. 本次 F05 原始完整路径可完成，随后六例离线生命周期完整通过。
2. 同一确认重复点击或重启后重放不增加调用；旧确认、伪造确认或未确认不能授权。
3. 正文、要求、来源或报告变化使旧确认失效；新核验仍可因证据缺口拒绝。
4. 独立代码和结果审核通过，重新封存候选与评测入口后才提出新一轮真实预算；旧 G01 证据不能自动授权不同候选。

本轮不实施此产品补丁，也不请求真实调用额度。
