# 严格证据核验

入口：模型与设置 → 严格证据核验。此功能为工作区开关，当前用户工作区已启用。

## 实际行为

1. 每轮生成前，从当前目标、完成标准、执行约定及有效补充建立稳定 ID 的要求清单。超过 80 项或序列化 24000 字符时，保留全文并要求拆分，不截掉要求继续生成。
2. 现有独立内容/结果检查调用同时返回关键结论和原文引用。应用校验当前稿件、来源范围、版本、精确字符位置及本轮实际可见范围。模型生成的任务描述、要求、旧稿和交付回读正文不能给业务事实自证；显式用户输入会标明其用户陈述来源。
3. 未完整阅读当前稿、缺要求、缺引用、引用不存在、来源权限失效、核验未通过时，保留草稿并阻断验收和对应正文交付。GitHub、飞书、Agent Outlook 发信在实际发送前再次检查；发送正文必须绑定已核验稿件。GitHub 的运输标记仅保留原始回读中精确匹配的后缀。
4. 启用时，已有未验收的待验收事项回到待检查，保留文稿与步骤。已验收历史不被自动重开。
5. 事项详情可展开上次核验中的要求、缺口、关键结论和原文。历史核验记录不代表当前版本仍有效。

## v3：来源分歧与交付阻断

来源彼此不同不必然使稿件不能交付。原要求允许证据不足时如实未知，且稿件确实披露分歧、不擅自选边时，独立 checker 可返回信息记录 `sourceConflicts`，使用 `disposition: "disclosed_unknown"`。每条记录必须给出具体理由，并绑定：

- 当前稿件中明确标注未知的 `unknown` 结论。普通结论检查和来源分歧检查共用 `UNKNOWN_MARKER` 词表，包括“无法确定”“无法判断”“不能确定”“无法得知”“未能确认”等明确未知措辞；普通的“未”不构成未知标记。只有“建议”“可能”等标记也不满足来源分歧的明确未知条件。
- 允许该未知结果的要求集合 `requirementIds`：所列要求均须判定满足，集合至少关联一个相关未知结论。全部原始要求仍独立核验；已经独立核对文本与引文的补充结论（例如标题）无需再反向关联某项要求。
- 至少两个不同的有效原文片段，可来自同一汇编或不同来源。每个关联未知结论都须持有该项全部引用；引用仍经过来源范围、权限、版本、逐字位置和本轮可见范围检查。

这不是对任意冲突的豁免。旧 `conflicts` 字符串仍一律作为交付阻断；`unsupportedClaims`、要求缺口、未完整阅读和整体 `passed:false` 也不会被来源信息记录覆盖。要求必须得到唯一确定答案、稿件隐去分歧或无依据选边时，仍须阻断。

任务是否允许未知、两段资料是否真正冲突，以及结论是否语义正确，继续由独立 checker 按原要求判断。程序检查上述绑定及引用条件，不能独自证明这些自然语言判断正确。

## v3：紧凑核验报告

新的模型输出使用显式 `format: "compact-v3"`：

```json
{
  "format": "compact-v3",
  "scannedArtifactIds": ["当前稿件ID"],
  "citations": [
    {"id":"e1","sourceId":"来源甲ID","quote":"冲突一方的逐字原文"},
    {"id":"e2","sourceId":"来源乙ID","quote":"另一方的逐字原文"}
  ],
  "requirements": [{"id":"当前要求ID","status":"satisfied","claimIds":["u1"]}],
  "claims": [{"id":"u1","artifactId":"当前稿件ID","text":"无法确定","kind":"unknown","supported":true,"citationIds":["e1","e2"]}],
  "unsupportedClaims": [],
  "conflicts": [],
  "sourceConflicts": [{"disposition":"disclosed_unknown","claimIds":["u1"],"requirementIds":["当前要求ID"],"citationIds":["e1","e2"],"reason":"具体说明双方分歧及为何原要求允许交付未知"}]
}
```

同一引文只在共享 `citations` 表输出一次，结论复用 `citationIds`。成功且有关联结论的要求、已获支持的结论可省略重复 `reason`；程序为界面生成简短说明并展开原有引用结构。缺口、延后检查、未获支持的结论，以及没有关键结论的格式/创作要求，仍需具体理由；`sourceConflicts` 的理由也不能省略。没有来源分歧时可省略该字段。

旧的结论内联 `citations` 报告仍可读取并校验，但不能与共享引用混用，也不能继承新格式的理由省略规则。未知格式、重复或不存在的引用 ID 均阻断。缓存版本升为 3，旧版本通过记录不能直接作为当前交付授权。

## Token 策略

- 使用现有检查调用，不新增固定第三轮评审；必要的 read_context 读取仍可能增加调用。
- 来源仍按需读取，不把全部原文每轮重复发送。
- v3 在模型输出中复用引文 ID，并省去可由关联结论展开的成功理由；保留完整要求覆盖和失败理由。实际节省须通过相同案例的真实 usage 验证。
- 要求、正文、来源版本、权限或相关背景变化会使报告失效。相同依据复用时只向模型提供计数，不重复发送引用正文。
- 本版保守地对任何正文变化重新核验；尚未按结论依赖进行局部复核。

### 核验输入协议 `verify-input-v1`

严格核验的 checker 使用合并后的独立核验说明和精简读取导航，避免同时发送生成者说明及多份相同备注。完整要求、用户原话、当前稿件、来源标识/版本、实际阅读范围和分页恢复信息仍照常提供；不压缩业务原文，也不把磁盘已有材料算作模型本轮已读。生成角色与关闭严格核验的路径保持原输入。

该变化保持 `version:3` 和 `format:compact-v3`；`groundingStatus.inputProtocol` 返回输入协议标识。严格模式的 exact 检查缓存 key 包含此标识，更新协议后不能直接命中旧提示的检查结果。事实核验缓存仍按原有要求、正文、来源及权限规则判断有效性。输入字符减少只是实现性质，实际总 token 和语义错误须用冻结实现及新样本对照判断。

## 证据边界

### 输入归因与回执投影 `verify-input-v2`

每次实际 transport attempt 在 `modelCalls[].inputAttribution` 保存固定说明、要求、稿件、证据正文、证据元数据、工具回执、目录及其他上下文的字符数和 UTF-8 字节数；运行明细也保留这些统计。最近模型调用及运行明细可展开查看。记录不包含输入正文，也不回灌模型。

模型返回的 input/output/cached token 是实测值。分类 token 仅按可见输入字节比例分摊，明确标为估算；不可当作 tokenizer 精确计数或缓存分类，也不能据此声称服务端额外开销已精确定位。未返回 usage 时保持未知。失败、重试、备用调用分别记录，原费用与预算规则不变。

严格模式的生成及核验输入，仅在同来源、版本、范围和全部结果字段相同且节省空间时用 `receiptRef` 复用回执。原文引用仍指向本次提供的真实正文。成功读回执中与外层相同的 canonical 资源/版本及与顶层相同的 contextRevision 不再重复发送；局部位置、未映射标记、权限版本、覆盖范围、续读请求和错误完整保留。解析器保存的原回执、阅读进度、权限/版本校验及交付规则不受投影影响。关闭严格模式仍使用原有输入。协议升级使严格模式的旧 exact 检查缓存失效。

程序校验来源与引用的一致性，独立模型判断是否支持结论。完整扫描、遗漏关键断言、反例发现仍受模型能力影响；引用真实也不能保证语义推理一定正确。外部部署参数继续使用既有逐次预览和授权，不冒充已完成文本事实核验。工作区中的独立手动工具不属于 Agent 事项正文交付链路。

离线回归测试使用合成资料、临时工作区和模拟模型。真实模型评测另经生产适配器执行，会消耗订阅额度，并保留原始输入、响应、usage 与独立语义复核记录；运行方法及口径见 [GROUNDING_LIVE_EVAL.md](GROUNDING_LIVE_EVAL.md)。

## 运行版本诊断

受信任应用 IPC 的只读 `groundingStatus` 动作返回当前 worker 的开关、核验版本、格式、能力标记和模块加载时捕获的源码 SHA-256。它不调用模型、不写工作区，也不进入日常模型上下文。将其哈希与预期实现比较，可确认运行中的 worker 是否加载了该代码；只读取磁盘文件不能证明旧进程已更新。该诊断不是语义正确性或安全性的证明，仍需回归测试及真实核验。
