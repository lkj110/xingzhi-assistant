# 表达标记疑义：人工确认闭环

本轮实现了通知表达标记疑义的有限人工分流：只有现有独立核验整体通过、全部本地证据检查通过、且仅剩通知 proposal 的表达标记疑义时，才进入“表达标记待人工确认”。此时核验结果仍为 `passed:false`，不交付、不完成、不进入普通待验收，也不自动重试或修稿。

## 用户操作与边界

1. 事项详情展示待确认原句及其逐字来源，用户判断表达是否已清楚区分安排与事实断言。
2. “确认这些表达已清楚”只保存人工判断，保持等待和未通过；不启动模型，不确认事实、批准、执行或验收。
3. 用户另行点击“重新核验”。只有同一完整依据、同一稿件和完全相同的表达可使用旧确认；模型每轮自由分配的 claim ID 只作审计，不能导致相同内容重复确认。同一依据下分批确认可累积，新增片段不会抹掉已确认片段；依据变化后不能继承。其他独立核验及本地硬检查重新执行。
4. 重新核验通过后进入普通待人工验收，受影响事项必须由用户按完整验收条件验收。即使开启自动完成或 Agent 自动验收，也不能自动完成；“人工完成”捷径也不能绕过这一流程。

来源身份、逐字引文、实际读取、要求覆盖、正文绑定、未解决冲突、未知/推断缺标记、无据结论及独立检查拒绝仍然硬拦。没有新增句式词表、通用语义推断或模型阶段。人工确认不能清除其他缺口；后置业务关联检查新增的缺口同样不能被降级。

来源、权限、要求、标题或正文改变时，旧确认依据失效。显式用户编辑/反馈会撤销旧等待，保留人工验收限制；来源变化后的专用重检可以刷新旧核验。重复反馈即使被要求清单去重，也能正常恢复。“重新核验”不会生成未完成步骤或改写正文；有修订工作时走原有修订流程。

## 实现与回归

主要逻辑集中在 `desktop/marker-confirmation.cjs`：人工确认身份、可信 UI 命令、等待分流和显式重检。`grounding.cjs` 保留原识别边界，仅将符合条件的剩余标记疑义交给人；最终核验和内容核验两个入口都接入等待，调度、自动修复、缓存及验收链共同维护同一边界。界面使用独立 `MarkerConfirmation` 组件。

526 项统一运行先于最终的完整标记列表保存、重复反馈恢复及分批确认累积修复；这些边界经过最终代码的 41 项定向复测。不能将重复运行相加当作新的独立样本数，也不把单元测试通过率当作业务流程完成率。

独立代码审核及最终检查发现并修复了编辑后等待无法恢复、自由 claim ID 引发重复确认、Agent 自动验收错误中断、超过 20 条/超长编号被截断、重复反馈后检查被清空，以及分批确认覆盖旧确认等问题。旧修复 episode 不再把人工表达疑问算成一次失败修稿，原核验记录仍结算为未通过。详见[验证证据](evidence/foundation-marker-confirmation-verification.json)和[独立审核](evidence/foundation-marker-confirmation-review.json)。

已暴露的 P01 只用于离线回归：补齐对象后的通知不再被当作必须自动修稿的错误，但仍保持未通过，等待人核对。测试中的核验响应为固定替身，不能证明真实模型能正确判断所有条件或事实。旧样本、参考稿、报告和封存未回写。

## 成本与交付状态

生成提示词保持 472 UTF-8 字节，独立核验提示词保持 2341 字节，二者逐字不变。模型协议/schema、输入封装和调用编排文件未变。人工确认记录和纯本地等待提示不进入模型输入。

人工确认命令为零模型调用；显式“重新核验”使用原有核验流程，可能含读取原文及多次模型交互，成本并非零。本轮未新增真实模型调用，不能声称总 tokens 下降，也没有新增真实幻觉率、误拦率或错误放行率结论。新的状态是待人工处理，不能在今后评测中算作核验通过或最终交付成功。

本轮只交付源码补丁。当前安装基础版的 86 个文件、旧候选包的 86 个文件，以及四套历史样本的 47 个文件均与冻结记录一致。没有重新打包或覆盖安装，尚不能说该补丁已在当前安装版生效。

下一步先制作独立候选包，离线验证“等待→人工确认→显式重检→手动验收”及重启恢复；通过后再准备一次有停止条件的小规模真实验收方案与预算。当前不启动正式主评测。
